# 多核 NPU 切图调度算法与实验方案

本文主要描述从队友交付的第二版继承的启发式及其数学含义。函数和数据结构见 [代码结构与函数说明](代码结构与函数说明.md)，每张图的读法见 [结果字段与图表解读](结果字段与图表解读.md)。第三版新增的确定性候选见 [第三版改进说明](第三版改进说明.md)；正式全量评估在 Windows 上运行。

## 一 问题与输出

输入是包含操作、张量及有向边的计算图，以及核心数 `K`。输出严格使用官方方案格式：`node_to_subgraph` 把每个非 `COPY_IN/COPY_OUT` 操作映射到一个非负子图 id；`core_schedules` 是长度为 `K` 的列表，每个核心按执行顺序列出子图 id。所有操作必须恰好出现一次，子图依赖图无环，同核顺序满足依赖。

记操作集合为 `V`，子图集合为 `S`，核心集合为 `C`。`x[v,s]∈{0,1}` 表示操作 `v` 属于子图 `s`，`y[s,c]∈{0,1}` 表示子图 `s` 在核心 `c`，`π_c` 表示核心 `c` 的子图顺序。基本约束为 `Σ_s x[v,s]=1`、`Σ_c y[s,c]=1`，以及子图商图无环、`π_c` 不逆转商图上的同核依赖。真正的 L1/UB 容量、四条 Pipe、DDR 共享带宽和 L2 FIFO 行为由官方评估器判定与模拟，不以启发式估计替代。

上述变量用于表达模型，不表示程序构造并精确求解了整数规划。当前求解器直接通过拓扑排序、区间切分、列表调度和有限邻域搜索构造这些决策。

如果用 `a_o`、`f_o` 表示操作开始和结束时刻，则模拟执行还需满足以下资源约束：依赖操作必须先完成；同一核心同一 Pipe 的操作区间不能重叠；每个核心在任意时刻的 L1 和 UB 驻留量分别不超过 524,288 和 131,072 bytes；所有真实进入 DDR 搬运池的并发访问共享总带宽 60 bytes/cycle。有 L2 时，Cache 命中读取进入独立的 250 bytes/cycle 共享池。DDR COPY 的时长随其他搬运加入和退出而变化，不能统一设为某个固定周期数。

场景 A 中，同核前一个 Task 完成后的 100 cycles 等待和跨核前驱完成后的 1,000 cycles 等待共同限制新 Task 激活。场景 B/L2 中，同核子图合并为一个 Task；跨核目标 COPY_IN 等源 COPY_OUT 完成后再经过 500 cycles 才能进入就绪判定。依赖图、Pipe 顺序和跨核 COPY 的组合仍可能导致不可执行等待，最终还需官方全局执行检查。

首要目标是最小化官方 Makespan `T(x,y,π)`；当两个方案 Makespan 相同，选择额外 DDR 搬运量 `D_extra` 更小者。程序用字典序 `(T,D_extra)` 比较正式评估结果。快速估计只决定哪些候选值得评估，不进入最终成绩。

可供解释的下界包括：最长依赖链的累计计算周期、各 Pipe 总工作量除以核心数，以及不可避免的 DDR 搬运字节量除以 60 bytes/cycle。这些下界不能直接相加，因为计算和搬运可以流水重叠；它们用于判断某个方案主要受依赖、计算资源还是带宽限制。

## 二 图预处理与候选切图

先调用官方格式校验，复用第一版 `_graph_view` 收缩原图中的 COPY 链，建立非 COPY 操作 DAG。对每条依赖记录近似字节权重和共享标记。共享标记由不超过 1 MiB、具有多个消费者的张量及其 COPY 收缩路径得出，不是对实际 Cache 命中的判定。生成三种确定性拓扑序：关键路径优先、共享依赖优先、低输出量代理优先。对各顺序尝试多个随操作数和核数缩放的目标子图大小；在允许的区间内，按“工作量偏差＋切口跨越字节量＋过大块内存压力”选切点。每个子图是一个拓扑序连续区间，因此初始子图商图不会因不连续合并而形成环。

关键路径优先级由逆拓扑递推 `rank(v)=max(1,cycles(v))+max rank(u)` 得到，`u` 遍历后继，无后继时第二项为零。共享依赖优先级先考虑已收缩的共享前驱边权总量。内存代理 `output_size[v]` 取该操作外出依赖的最大权重；它不是所有输出张量大小的精确总和，也不分析真实生命周期。切分时用前缀和计算区间工作量，并用跨越当前切口的边权估计通信。候选目标块大小先取 `max(32,min(512,ceil(|V|/(7K))))`，乘 `0.65、1、1.55、2.25` 四档系数，再限于 24～512 并去重。切口可以在目标大小附近移动，因此 512 不是实际子图操作数的严格上限。

这种切法仍是近似：输出依赖权重的累加只是缓存压力代理，不能准确预测换入换出。粗估阶段把 L1/UB 容量相加用于压力评分；正式评估仍分别约束两种私有存储。每个候选必须通过官方 `derive_multicore_plan`，正式结果以评估器为准。第一版方案也作为候选参加正式评估和最终回退。

## 三 子图分核和场景差异

对子图依赖图做就绪列表调度。列表优先级取块内操作 rank 的最大值；每个就绪子图试放到所有核心，估计当前核心空闲时刻、前驱完成时刻、搬运时间、场景同步延迟、各 Pipe 工作量和缓存压力，按“预计完成时刻＋少量通信惩罚”选择核心。该过程同时确定核心分配与每核子图顺序。

对于子图 `s`，用 `W[s,p]` 表示其非 COPY 操作在 Pipe `p` 上的 `max(1,cycles)` 总和，基础时长代理取 `max_p W[s,p] + 0.15(Σ_p W[s,p] - max_p W[s,p])`。原图 COPY 已在图预处理中收缩，此处不等于完整四条 Pipe 的真实工作量。跨边近似大小为 `b` 时，DDR 往返传输代理取 `2b/B_DDR` cycles，固定配置下 `B_DDR=60`；实际并发搬运共享总带宽，因此该式仅用于候选排序。缓存压力代理依据块内输出代理量和 L1/UB 总容量构造，在正式评估中仍由核内调度算法决定是否换出。

**问题一 场景 A。** 每个子图独立成为 Task，同核也不保留跨 Task 张量。估计所有跨子图边的 DDR 中转，分别计入同核 Task 等待与跨核前驱等待。较大的子图往往降低通信与等待，但可能削弱并行度，因此保留多档粒度候选。

**问题二 场景 B。** 每核的子图合为一个 Task；同核依赖可以直接保留片上数据，跨核依赖需 DDR 中转和同步等待。因此优先将强数据依赖放在同核，同时通过关键路径和 Pipe 工作量避免负载失衡。块内输出量用于惩罚可能导致大量换入换出的过大子图。

**问题三 L2。** 在场景 B 基础上，对可复用的共享输入给予通信折扣，以引导候选形成更可能命中只读 FIFO Cache 的访问次序。折扣仅影响候选排序；最终由官方 1 MB 容量、250 bytes/cycle 独立带宽的模拟结果决定。程序始终保留题二方案在有 L2 时的正式成绩作为题三候选下限。

当前 L2 估计的具体做法是：跨核边汇总具有共享标记时，把估计传输代价乘 0.45。它没有在候选阶段模拟 FIFO 队列、复用距离、访问时刻或 Cache 带宽；这些由官方模拟器处理。不能把该折扣描述成已经实现的精确 Cache 调度模型。

### 当前启发式系数

| 位置 | 当前取值或公式 | 意义 |
|---|---|---|
| 候选原始数量 | 三种顺序 × 最多四档粒度 | 最多十二种，再筛选最多两个进行正式评估 |
| 切口范围 | 从当前起点后的约 `0.65target` 到 `1.3target` | 在工作量和跨边成本间挑选位置 |
| 切口评分 | 相对工作量偏差 `+0.18×crossing/max(target_work×60,1)+0.08×pressure` | 此处的 60 是代码中的归一化常量，与当前固定带宽一致 |
| 压力代理 | `max(0,块内 output_size 总和/总容量−3)` | 不表示真实溢出字节 |
| 时长压力系数 | 基础时长乘 `1+min(0.5,0.03×pressure)` | 增加过大块的近似代价 |
| 选核心 | 最小化 `finish+0.03×traffic` | traffic 为该核心选择下估计传输时间之和 |
| 候选总分 | `max(core_end)+0.15×total_transfer+0.01×total_pressure` | 分数越小越优先评估，不是正式 cycles |

这些系数是实现中的启发式取值，尚不能以现有三例验证宣称为全量调参得到的最优值。后续可做消融实验，但正式成绩仍使用题目规定的硬件配置。

调度代理只实现快速排序，没有重新实现官方离散事件模拟。特别是 DDR 争用、Task 内乱序执行、Belady 式换出与 L2 FIFO 淘汰可能使代理排序与最终成绩不一致。因此候选池始终交给官方评估器决定，并通过第一版回退限制退化风险。

## 四 正式评估和局部搜索

每个用例、场景、核数先评估第一版方案及快速估计最高的两个不同候选。只有官方评估成功的候选才有资格入选；从中按 `(Makespan, 额外搬运量)` 取最优。这样题一、题二最终结果在相同评估器下不会劣于第一版。题三另保留题二最终方案的有 L2 结果。

全部必需评估完成后，在时间预算内对当前方案尝试五类局部变化：迁移一个子图、交换两核子图、合并同核相邻子图、交换无冲突的同核顺序、拆分一个大子图。当前每组配置只从进入搜索时的方案生成一批、最多五个合法邻居，比较后保留最佳；没有实现不断迭代到局部最优的多轮搜索。每个邻居先过官方方案校验，再做正式评估；只有字典序成绩更好才替换原方案。搜索记录与必需评估分开保存；题二方案变化后还须刷新受影响的题三配对。

复杂度应区分阶段：图遍历、前缀和与切口扫描主要随操作和边数增长；使用堆的就绪拓扑排序包含 `O(|V|log|V|)` 开销，子图分核还包含堆操作和对 K 个核心的试放；官方方案校验有独立成本。因此不能将整个实现严格称为线性时间算法。三种顺序、有限粒度与最多两个正式候选控制了搜索规模，官方评估通常占现实运行时间的大部分。

`--search-hours` 到期后停止提交新的搜索任务，已经启动的任务及保持题三配对一致性的重算可能继续运行。100 例必需评估不受这个预算截断，但仍有 worker 超时；必需结果缺失会使运行不完整，可选搜索候选失败则单独记录。

## 五 指标、比较和图表

对用例 `i` 和 `k` 核方案，题一、二的加速比定义为 `S[i,k] = T_single[i] / T[i,k]`，其中 `T_single` 来自官方单核调度。正文的平均加速比取全部用例 `S[i,k]` 的算术平均；单核点按题目定义为 1。还报告第一版相对提升 `T_v1/T_selected`、胜率、Makespan 与额外搬运量，避免只凭单一平均值判断性能。

题三先固定题二最终方案 `P_B[i,k]`，分别运行无 L2 和有 L2 的官方评估。Cache 自身加速比定义为 `T_noL2(P_B)/T_L2(P_B)`；逐用例报告两个 Makespan、额外搬运量和按字节的 Cache 命中率。另行优化的题三方案 `P_L2` 单独列出，其收益包含方案变化，不能当成纯 Cache 效果。单核也对同一整图方案做无 L2／有 L2 配对评估，供 1～5 核曲线使用。

每次运行按时间戳隔离，`manifest.json` 记录用例、核数、固定配置哈希、运行参数、Python 版本与完成状态。逐组 JSON 是事实来源，CSV 与 PNG 可重建。出现超时、非法方案或评估异常时，记录错误并继续其他任务；缺失必需结果则整体标记为 `incomplete`。

此算法是可复现启发式，不声称全局最优。特别大的图可能令整图单核基准及官方评估耗时较长；此时优先保留已完成结果并在更强 CPU 上续跑。论文中必须明确区分第一版、第二版和同方案 Cache 对照，并如实报告完成用例数与失败项。
